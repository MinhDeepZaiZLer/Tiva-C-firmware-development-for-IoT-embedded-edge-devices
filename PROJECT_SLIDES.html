Problem Statement


Deployed IoT devices cannot be physically accessed for firmware updates.


A device installed in a cabinet, on a pole, or underground — the only way to update its software is over the air.


Challenge: The device is running the firmware it needs to update.

Flash is execute-in-place — you cannot overwrite code you are currently executing.


Solution: Staged flash regions + a first-stage bootloader.

Flash Memory Layout

 256 KB total flash on TM4C123GH6PM:

 0x00000 ┌──────────────────────────────┐
         │   BOOTLOADER (3.3 KB)        │  0x0000 – 0x3FFF
         │   Validate → Erase → Copy    │
         │   → Jump (inline asm)        │
 0x04000 ├──────────────────────────────┤
         │   APPLICATION (30 KB)         │  0x4000 – 0xBFFF
         │   Sensors + MQTT + FOTA       │
         │   VTOR relocated to 0x4000    │
 0x10000 ├──────────────────────────────┤
         │   STAGING HEADER (1 KB)       │  0x10000 – 0x103FF
         │   magic(4) + size(4) +        │
         │   SHA-256(32) + reserved(88)  │
 0x10400 ├──────────────────────────────┤
         │   STAGING IMAGE (30 KB)       │  0x10400 – 0x17FFF
         │   Downloaded firmware          │
         │   Written chunk-by-chunk       │
         └──────────────────────────────┘

 Key: sector size = 1 KB. Image @ 0x10400 is sector-aligned
      so header erase at 0x10000 never touches the image.

Constants match exactly between ota.c and bootloader.c.

Phase 4 — FOTA Pipeline

  TB assigns firmware 1.0.3
      ↓
  [STEP A] Receive metadata (MQTT PUBLISH on attributes)
      ↓
  [STEP B] Report DOWNLOADING
      ↓
  [STEP C] Download via MQTT chunks (v2/fw/request/0/chunk/<index>)
           → Flash to staging (0x10400), SHA-256 streaming verify
      ↓
  [STEP B] Report DOWNLOADED → VERIFIED
      ↓
  [STEP C] Write swap header at 0x10000 (magic + size + SHA-256)
      ↓
  [STEP D] Reset → Bootloader validates header
           → Erases app (0x4000) → Copies staging → app
           → Clears header → Jumps to new app
      ↓
  [STEP B] Report UPDATED → version match → no re-download loop

Step A — Receive Metadata

// App_Ota_ProcessMessage() — Common/ota.c
void App_Ota_ProcessMessage(const MqttMessage *msg) {
  if (strstr(msg->topic, "attributes") == 0) return;

  // Extract fw_* fields — handles flat AND {"shared":{...}} formats
  App_JsonCopyString(ota_metadata.title, ..., msg->payload, "fw_title");
  App_JsonCopyString(ota_metadata.version, ..., msg->payload, "fw_version");
  App_JsonCopyString(ota_metadata.checksum, ..., msg->payload, "fw_checksum");
  App_JsonGetUint(msg->payload, "fw_size", &ota_metadata.size);

  // fw_url typically absent — code uses MQTT chunk API instead
  ota_metadata_valid = 1;
  App_Ota_ReportState("DOWNLOADING");
  App_Ota_DownloadFirmware();
}

JSON parsing: heap-free, minimal, searches entire payload for each key.

Step C — Download Loop

while (offset < meta->size) {
  // 1. Erase flash sector on 1 KB boundary
  if ((offset & 0x3FFu) == 0u) FlashErase(OTA_IMAGE_BASE + offset);

  // 2. Request chunk
  Mqtt_RequestFwChunk(0u, offset / OTA_CHUNK_SIZE, OTA_CHUNK_SIZE);

  // 3. Wait for response (8s timeout, 200ms poll)
  while (waited < 8000u) {
    if (Mqtt_ReadPublish(&msg, 200u))
      if (strncmp(msg.topic, "v2/fw/response/", 15u) == 0) { got=1; break; }
    waited += 200u;
  }

  // 4. Program flash (pad to 4-byte alignment)
  FlashProgram((uint32_t *)prog_buf, OTA_IMAGE_BASE + offset, prog_len);

  // 5. Streaming SHA-256 verify
  Sha256_Update(&sha, prog_buf, recv);
  offset += recv;
}
// After loop: SHA-256 final → compare → write header if match

Step D — Bootloader Swap

// Bootloader/bootloader.c — runs on every reset
int main(void) {
  Boot_UartInit();
  Boot_SwapFirmware();          // check staging → copy if valid
  if (Boot_IsApplicationValid())
    Boot_JumpToApplication();   // never returns
  while (1) {}                  // halt if no valid app
}

static int Boot_SwapFirmware(void) {
  const OtaSwapHeader *hdr = (const OtaSwapHeader *)STAGING_BASE;
  if (hdr->magic != SWAP_MAGIC) return 0;         // no staged image
  if (hdr->size == 0 || hdr->size > FLASH_SIZE) return 0;

  Boot_FlashEraseApplication(hdr->size);           // erase 1 KB sectors
  // Copy 0x10400 → 0x4000 in 256-byte chunks
  while (remaining > 0) { Boot_FlashWrite(dst, src, chunk); ... }
  FlashErase(STAGING_BASE);                        // clear header
  return 1;
}

Jump: inline assembly — cpsid i; msr msp; bx — because C stack is invalid after MSP switch.

Demo — OTA Cycle (End-to-End)

  1. Flash project0_merged.bin via LM Flash Programmer (one-time)
      ↓
  2. Device boots → connects WiFi → connects MQTT → publishes telemetry
      ↓
  3. In ThingsBoard: upload new .bin as OTA package (v1.0.3)
      ↓
  4. Device receives metadata (Step A)
  5. Reports DOWNLOADING (Step B)
  6. Downloads via MQTT chunks (Step C) — SHA-256 streaming verify
  7. Writes swap header at 0x10000
  8. Reports VERIFIED (Step B)
      ↓
  9. Reset → Bootloader swaps staging → app (Step D)
  10. New app runs → reports UPDATED (Step B)
  11. Version matches → no re-download → loop ends

Full cycle: ~2 minutes (30 KB download at 1 KB/chunk over MQTT).

Security Considerations

Implemented

  • SHA-256 integrity verification
  • Version-skip defense (no re-download)
  • Credentials in gitignored config_user.h
  • Application validation before jump
  • Header cleared after swap (no replay)

Not yet implemented

  • TLS encryption (plain MQTT, port 1883)
  • Code signing (SHA-256 only, not authenticated)
  • Encrypted firmware images
  • Rollback on failed boot
  • Secure boot chain

For production: TLS (port 8883) + certificate pinning + code signing is required.

Lessons Learned

Embedded Design

  • Keep bootloader tiny — 3.3 KB, one job: validate → copy → jump
  • Flash layout is a contract — mismatch between build stages → silent corruption
  • Sector-aligned addresses — prevent cross-sector erase destroying data
  • Streaming crypto — no full-image RAM buffer on 32 KB SRAM

Communication

  • State machines for unreliable streams — ESP8266 +IPD splits require persistent mode
  • TB session routing — chunk responses arrive without subscription
  • MQTT keepalive needs polling — 100ms intervals, not blocking sleep

Build System

  • CCS makefiles are fragile — manual sync of subdir_vars.mk + ORDERED_OBJS
  • Use tiarmobjcopy — tiobj2bin post-build fails silently
  • Always clean build after makefile changes

Memory

  • Stack overflow → silent corruption — 256 B stack caused mysterious failures
  • Check .map file for stack usage before debugging symptoms
  • Static buffers for large data — 2 KB UART/MQTT buffers can't fit on stack

Process

  • Write docs while building — decisions are fresh, rationale is clear
  • Commit small, commit often — 38 commits, each with a clear message

Best Practices Summary

ArchitectureLayered design: Drivers → MQTT → OTA → Bootloader. Each layer independently testable.
Flash SafetySector-aligned regions. Header erase never touches image. Atomic "ready" flag (write header last).

Conclusion


What we built:

A complete embedded IoT system — from bare-metal UART drivers to cloud-managed firmware updates — in ~3,140 lines of C with no external frameworks beyond TivaWare HAL.


Key achievements:

  • Full FOTA pipeline (Steps A–D) verified on real hardware
  • 30 KB application + 3.3 KB bootloader = 33 KB total
  • SHA-256 streaming verification — no full-image RAM buffer
  • Persistent +IPD state machine handles all ESP8266 quirks
  • 5 real incidents found, diagnosed, and documented with fixes
  • 38 git commits with clear, traceable history

What remains:

Production hardening: rollback, persistent state, TLS, code signing.
