What is FOTA?

Firmware Over-The-Air — update embedded software remotely via WiFi, no physical access required.


Analogy: Like your phone updating apps over WiFi.

Reality: The device is "running the firmware it needs to update".


Core problem: Flash is execute-in-place. You cannot overwrite the code you are currently executing.

Solution: Staged regions + a bootloader that runs before the application.

Why FOTA is Hard

Constraint 1: Flash cannot self-overwrite

Must erase sector first (destructive), then program. Running code in that sector → crash.


Constraint 2: Power loss at any moment

Partial write → corrupted image. Must guarantee old firmware survives.

Constraint 3: Limited RAM (32 KB)

Cannot buffer entire firmware image in RAM. Must stream to flash.


Constraint 4: Unreliable network

WiFi drops, TCP segments split. Must resume, not restart.

ESP8266 AT Command Primer

ESP8266 does not run user code. All networking is done via AT commands:

AT                          # → "OK" — alive check
AT+CWMODE=1                 # Station mode
AT+CWJAP="SSID","PASS"      # Join WiFi AP
AT+CIFSR                    # Get IP address
AT+CIPSTART="TCP","host",1883  # Open TCP socket
AT+CIPSEND=10               # Prepare 10 bytes of data
# → ">" prompt → send raw bytes → "SEND OK"
# Incoming data arrives as: +IPD,<len>:<data>

Key quirk: ESP8266 NonOS AT firmware splits large TCP receives across multiple +IPD frames, and sometimes sends raw continuation bytes without +IPD header.

Flash Memory Layout

 256 KB total flash on TM4C123GH6PM:

 0x00000 ┌─────────────────────────────┐
         │   BOOTLOADER (3.3 KB)       │  0x0000 – 0x3FFF
         │   Runs first on every reset  │
         │   Checks staging → swaps    │
         └─────────────────────────────┘
 0x04000 ┌─────────────────────────────┐
         │   APPLICATION (30 KB)        │  0x4000 – 0xBFFF
         │   Sensors, MQTT, FOTA logic  │
         └─────────────────────────────┘
 0x10000 ┌─────────────────────────────┐
         │   STAGING HEADER (1 KB)      │  0x10000 – 0x103FF
         │   magic + size + SHA-256     │
 0x10400 ├─────────────────────────────┤
         │   STAGING IMAGE (30 KB)      │  0x10400 – 0x17FFF
         │   Downloaded firmware         │
         └─────────────────────────────┘

Why Split Flash?

Bootloader runs first

Even if app is corrupted, bootloader still works — can recover with next upload.


App never self-erases

Erasing flash destroys executing code. Download to staging (separate region), let bootloader copy.

Staging isolated

Power loss during download → staging is corrupt, but old app is untouched → bootloader skips swap.


Header as signal

Writing the header at 0x10000 is the last step — an atomic "new image ready" flag.

Overall FOTA Flow

TB assigns firmware 1.0.3 to device
    ↓
TB pushes shared attributes: fw_title, fw_version, fw_size, fw_checksum...
    ↓
[STEP A] APP receives metadata via MQTT PUBLISH
    ↓
[STEP B] APP reports DOWNLOADING to TB
    ↓
[STEP C] APP downloads firmware via MQTT chunk API
         → writes flash staging (0x10400)
         → SHA-256 streaming verify
    ↓
[STEP B] APP reports DOWNLOADED → VERIFIED
    ↓
[STEP C] APP writes HEADER at 0x10000
         (magic + size + SHA-256 = "new image ready")
    ↓
[STEP D] BOOTLOADER runs (on reset)
         → reads HEADER at 0x10000
         → sees SWAP_MAGIC → valid
         → erases app (0x4000)
         → copies staging (0x10400) → app (0x4000)
         → clears HEADER (prevents swap loop)
         → jumps to new app
    ↓
[STEP B] APP reports UPDATED to TB
         → version matches CONFIG_FW_VERSION → no re-download
         → loop ends

Step A — Packet Reassembly

ESP8266 splits MQTT PUBLISH packets across multiple +IPD frames:

+IPD,50:<mqtt-header-10-byte + 10-byte payload part 1>
+IPD,40:<30-byte payload part 2>
# Sometimes arrives as raw bytes (no +IPD header) — NonOS AT quirk

3-mode persistent state machine in UART1_ReadTcpBytes():

// Drivers/UART/uart1.c — state machine
typedef struct {
  uint8_t mode;       // 0 = scanning for tag, 1 = length digits, 2 = data
  char hdr[5];        // sliding window for "+IPD," detection
  uint32_t remaining; // bytes left in current frame
  char ok_win[7];     // sliding window for "SEND OK" detection
  uint8_t send_ok;    // flag set when "SEND OK" seen
} Uart1IpdState;

Handles: split headers, raw continuation bytes, overlapping SEND OK.

MQTT PUBLISH Reassembly

// Common/mqtt.c — Mqtt_CompletePublish()
// Reads +IPD chunks into mqtt_rx_raw[2048] until the PUBLISH packet
// whose header is already buffered is complete.
static uint32_t Mqtt_CompletePublish(uint32_t n, uint32_t timeout_ms) {
  while (n < sizeof(mqtt_rx_raw)) {
    int status = Mqtt_DecodePublishLen(mqtt_rx_raw, n, &total);
    if ((status > 0) && (total <= n))
      break;           // fully buffered — parse it
    // ...read more +IPD chunks...
    got = UART1_ReadTcpBytes(mqtt_rx_raw + n, ...);
    n += got;
  }
  return n;
}

This ensures the full PUBLISH packet is in mqtt_rx_raw before parsing topic + payload.

void App_Ota_ReportCurrentFirmware(void) {

    Sha256_Update(&sha, (const uint8_t *)(APP_BASE_ADDR + i), 256u);

Step C — Download Pipeline (4 Layers)

Layer 4: App_Ota_DownloadFirmware()    ← chunk loop + flash write + SHA-256
    ↓ MQTT publish/subscribe
Layer 3: Mqtt_RequestFwChunk()         ← builds v2/fw/request/.../chunk/...
    ↓ AT+CIPSEND
Layer 2: Mqtt_SendPacket()             ← pumps state machine, captures early frames
    ↓
Layer 1: UART1_ReadTcpBytes()          ← +IPD state machine, 3-mode parser
    ↓
Hardware: UART1 ISR → circular buffer  ← interrupt-driven, 2 KB buffer

Each layer is independent and testable. Layer 1 handles all ESP8266 quirks so higher layers see clean byte streams.

Step C — UART1 State Machine Detail

  scan mode (0)              length mode (1)           data mode (2)
  ┌──────────┐              ┌──────────┐              ┌──────────┐
  │ Sliding  │  "+IPD"      │ Parse    │  ":"         │ Read N   │
  │ window   │──────────→   │ digits   │──────────→   │ bytes    │
  │ matching │              │ → N      │              │ into     │
  └──────────┘              └──────────┘              │ buffer   │
       ↑                                                  │
       │             N bytes read, or timeout              │
       └──────────────────────────────────────────────────┘

  Also watches for "SEND OK" in scan mode (sliding window, separate path).
  Prebuf[128]: bytes captured during SEND OK wait → returned on next read.
if (g_ipd.mode == 2u) {           // data mode — read bytes
  data[written++] = ch;
  g_ipd.remaining--;
  if (g_ipd.remaining == 0u) g_ipd.mode = 0u;  // back to scan
} else if (g_ipd.mode == 1u) {    // length mode — parse digits
  if (ch >= '0' && ch <= '9') g_ipd.remaining = g_ipd.remaining * 10 + (ch - '0');
  else if (ch == ':') g_ipd.mode = 2u;
} else {                           // scan mode — find "+IPD,"
  // sliding window matching, also calls Uart1_ScanWatch(ch) for SEND OK
}

Step C — Download Loop

while (offset < meta->size) {
  // 1. Erase flash sector (1 KB boundary)
  if ((offset & 0x3FFu) == 0u)
    FlashErase(OTA_IMAGE_BASE + offset);

  // 2. Request chunk
  Mqtt_RequestFwChunk(0u, offset / OTA_CHUNK_SIZE, OTA_CHUNK_SIZE);

  // 3. Wait for response (8s timeout)
  while (waited < 8000u) {
    if (Mqtt_ReadPublish(&msg, 200u)) {
      if (strncmp(msg.topic, "v2/fw/response/", 15u) == 0) { got = 1; break; }
    }
    waited += 200u;
  }

  // 4. Program flash (pad to 4-byte alignment)
  memcpy(prog_buf, msg.payload, recv);
  prog_len = (recv + 3u) & ~3u;
  for (k = recv; k < prog_len; k++) prog_buf[k] = 0xFFu;
  FlashProgram((uint32_t *)prog_buf, OTA_IMAGE_BASE + offset, prog_len);

  // 5. Streaming SHA-256 verify
  Sha256_Update(&sha, prog_buf, recv);
  offset += recv;
}

Step C — SHA-256 Streaming Verify

Sha256_Init(&sha);

// ... during download loop ...
Sha256_Update(&sha, prog_buf, recv);  // fed chunk by chunk, never full image in RAM

// ... after all chunks received ...
Sha256_Final(&sha, digest);

// Compare with expected (parsed from fw_checksum hex string)
if (memcmp(digest, expected, 32u) == 0u) {
  // Write swap header at 0x10000
  OtaSwapHeader hdr;
  hdr.magic = OTA_SWAP_MAGIC;   // 0x53574150 = "SWAP"
  hdr.size  = meta->size;
  memcpy(hdr.sha256, digest, 32);

  FlashErase(OTA_STAGING_BASE);            // erase 0x10000 (1 KB sector)
  FlashProgram(&hdr, OTA_STAGING_BASE, sizeof(hdr));
  App_Ota_ReportState("VERIFIED");
}

Complete SHA-256 implementation is in ota.c (compact, no library dependency). Processes 64-byte blocks. Total RAM: Sha256_Ctx = ~136 bytes.

int main(void) {

  Boot_Print("[BL] bootloader up\r\n");

Step D — Swap Logic

static int Boot_SwapFirmware(void) {
  const OtaSwapHeader *hdr = (const OtaSwapHeader *)STAGING_BASE;

  // 1. Check magic
  if (hdr->magic != SWAP_MAGIC) return 0;  // no staged image

  // 2. Validate size
  if (hdr->size == 0u || hdr->size > (BOOT_FLASH_END - BOOT_APP_BASE))
    return 0;

  // 3. Erase application flash (1 KB sectors, rounded up)
  if (!Boot_FlashEraseApplication(hdr->size)) return 0;

  // 4. Copy staging → app (256-byte chunks)
  uint32_t remaining = hdr->size;
  uint32_t src = IMAGE_BASE;   // 0x10400
  uint32_t dst = BOOT_APP_BASE; // 0x4000
  while (remaining > 0u) {
    uint32_t chunk = (remaining > 256u) ? 256u : remaining;
    Boot_FlashWrite(dst, (const uint8_t *)src, chunk);
    src += chunk; dst += chunk; remaining -= chunk;
  }

  // 5. Clear header — prevents swap on next reset
  FlashErase(STAGING_BASE);
  return 1;
}

Step D — Application Validation

static int Boot_IsApplicationValid(void) {
  uint32_t initial_sp    = HWREG(APP_BASE);      // word at 0x4000
  uint32_t reset_handler = HWREG(APP_BASE + 4u);  // word at 0x4004

  // SP must be in SRAM (0x20000000 – 0x20008000)
  if ((initial_sp < SRAM_BASE) || (initial_sp >= SRAM_END))
    return 0;

  // Reset handler must be in flash, within app region, with Thumb bit set
  if ((reset_handler < (APP_BASE + 4u)) ||
      (reset_handler >= FLASH_END) || ((reset_handler & 1u) == 0u))
    return 0;

  return 1;
}

Why two checks?

• SP in RAM → vector table was written (not all 0xFF or random).

• Reset handler in flash + thumb bit → valid function pointer, not garbage.

• Together: prevents crash-loop if flash write was interrupted mid-erase.

Step D — Handover (Assembly)

static void Boot_JumpToApplication(void) {
  uint32_t initial_sp    = HWREG(APP_BASE);
  uint32_t reset_handler = HWREG(APP_BASE + 4u);

  HWREG(NVIC_VTABLE) = APP_BASE;  // relocate vector table

  __asm volatile(
      "cpsid i       \n"   // disable interrupts
      "dsb           \n"   // data synchronization barrier
      "msr msp, %0   \n"   // switch to application's stack pointer
      "isb           \n"   // instruction synchronization barrier
      "bx  %1        \n"   // branch to application reset handler
      :
      : "r"(initial_sp), "r"(reset_handler)
      : "memory");

  while (1) {}  // unreachable
}

Why assembly?

After msr msp, the C execution environment (old stack) is destroyed. No C code can execute after this point — not even the function call. Assembly is the only safe way to hand over.

Incident 1: JSON Truncated

Symptom: fw_* fields parsed as empty strings.

Cause: ESP8266 sends data via +IPD frames. A single MQTT PUBLISH can be split across 2–3 +IPD chunks. The old readline-based parser stopped at the first \n → lost data.


Fix: Wrote UART1_ReadTcpBytes() — a persistent 3-mode state machine that handles split +IPD headers, raw continuation bytes, and overlapping SEND OK.

// The state machine maintains mode across reads — no data lost
typedef struct {
  uint8_t mode;       // 0=scan, 1=length, 2=data — persists between calls
  char hdr[5];        // sliding window for "+IPD," detection
  uint32_t remaining; // bytes left in current +IPD frame
} Uart1IpdState;

Incident 2: Subscribe Rejected (0x80)

Symptom:

SUBACK bad: n=5 [90 03 00 03 80]
OTA download: subscribe FAILED

Cause: ThingsBoard Cloud always rejects SUBSCRIBE on v2/fw/response/#. This is a TB design decision — chunk responses are routed to the requesting MQTT session automatically.


Fix: Remove the subscribe command entirely. Chunk responses arrive via session routing. Code comment:

// ThingsBoard always rejects SUBSCRIBE on v2/fw/response/# with 0x80
// (unsupported topic) — chunk responses are routed to the requesting
// session regardless of any subscription, so none is needed.

Incident 3: Infinite Download Loop

Symptom: App downloads → reset → re-downloads → reset → re-downloads …

Cause:

CONFIG_FW_VERSION = "1.0.0" in code, but TB assigned version 1.0.2. Device reported current_fw_version = "1.0.0" → TB saw mismatch → pushed metadata again → infinite loop.


Fix (2 layers):

// Layer 1: Sync version
#define CONFIG_FW_VERSION "1.0.3"  // must match TB package version

// Layer 2: Defense-in-depth at download entry
if (meta->version[0] != '\0' &&
    strcmp(meta->version, CONFIG_FW_VERSION) == 0) {
  App_Ota_ReportState("UPDATED");  // skip download
  return 1;
}

Incident 4: Header Erase Destroyed Image

Symptom: After download, header erase destroyed first 128 bytes of firmware → vector table corrupted → crash.


Cause:

  HEADER at 0x10000, IMAGE at 0x10080  ← overlap!
  FlashErase(0x10000) clears sector 0x10000–0x103FF
  → destroys 0x10080–0x103FF (896 bytes of image)

Fix: Move image to 0x10400 (sector-aligned). Header gets entire 1 KB sector.

  HEADER at 0x10000–0x103FF  (sector 0)
  IMAGE  at 0x10400–0x107FF  (sector 1)  ← no overlap
  FlashErase(0x10000) only clears header sector.

Incident 5: ESP8266 AT Fail

Symptom:

TX> AT
AT: FAIL
ESP8266 setup failed; MQTT stopped

Cause: Board reset only resets the TM4C123, not the ESP8266. ESP stuck in a bad state from the previous session.


Fix: Power-cycle (unplug USB, wait 10 seconds, reconnect). This is a hardware limitation, not a code issue.

Prevention: Added AT+CIPCLOSE on MQTT reconnect and AT+CWQAP before re-association.

Lessons Learned

CategoryLesson
BootloaderKeep it tiny (3.3 KB). One job: validate → copy → jump. No networking.
Flash layoutConstants are a contract between build stages. Mismatch → silent corruption.
Sector alignmentAlways align regions to sector boundaries (1 KB on TM4C). Prevents cross-sector erase.
ESP8266 quirksHandle +IPD splits in state machines, not string matching. Persistent mode across reads.
Stack budget256-byte stack caused silent corruption. 2048 bytes + static buffers fixed it.
Version syncCONFIG_FW_VERSION must match TB package. Add defense-in-depth version check.
SHA-256 streamingNo full-image RAM buffer. Feed chunks as they arrive — critical for 32 KB SRAM.
TB routingv2/fw/response/# subscription rejected. Session routing handles it automatically.

Best Practices Summary

Design

  • Single-purpose bootloader
  • Sector-aligned flash regions
  • State machines for unreliable streams
  • Streaming crypto (no full-image buffer)

Build

  • Always gmake clean after makefile changes
  • tiarmobjcopy over unreliable tiobj2bin
  • Sanity-check merged binary (SP validation)

Debug

  • UART0 logging at every decision point
  • Hex dump of unexpected responses
  • Layer-by-layer testing (UART → MQTT → OTA → Boot)

Security

  • Credentials in gitignored config_user.h
  • SHA-256 integrity check (not encryption)
  • Defense-in-depth (version check + state machine)
